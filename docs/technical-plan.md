# 桌面猫技术方案

macOS 原生桌面宠物，形象来自真实的猫：会走动、有猫的动作、能交互。Windows 不在当前范围内。

**依据：** 阅读 OHM Pet、DyberPet、desktopPet、libshijima、Shijima-Qt、shimeji-ee、myCat、Neko、Petdex、hatch-pet 的源码和文档。这些项目都没有构建或运行，下文的设计也还没有原型验证。

## 1. 总体决定

| 决定 | 选择 | 原因 |
|---|---|---|
| 技术栈 | Swift + AppKit + CALayer | 只做 macOS，依赖最少 |
| 窗口 | 一个随猫移动的小窗口（无激活 NSPanel） | 看过的项目都用小窗口，没有全屏覆盖层 |
| 动作 | 由 JSON 定义，加动作不改代码 | OHM Pet、Neko 把行为写死在代码里，扩展困难 |
| 素材 | 2D 逐帧，暂定像素风，待实验确认 | 风格对比和生成实验尚未完成 |

## 2. 窗口与移动

- **窗口：** 无边框、不抢焦点、不进 Dock，可出现在所有桌面和全屏应用的辅助层。
- **点击穿透：** 根据缓存的透明度蒙版，在鼠标靠近时切换 `ignoresMouseEvents`，让透明像素的点击落到下层应用。参考项目都没有现成的 AppKit 逐像素方案。
- **在窗口上走：** 用 `CGWindowListCopyWindowInfo` 读取窗口位置和前后顺序，减去被遮挡部分，得到可走的线段。
- **窗口变化：** 小幅移动时猫跟着走；窗口快速移动、缩小、关闭，或脚下被遮挡时，猫掉下来。
- **多屏：** 统一使用一套全局坐标，只在一处转换 CG 坐标。左右相邻的屏幕走过去，上下相邻的跳过去。默认地面是 `visibleFrame` 底边，不压住 Dock。
- **循环：** 移动时用 display link 跑固定步长物理（30～60Hz），精灵图 8～12 帧/秒。闲置时停掉循环，只按下一个事件的时间唤醒。睡眠或锁屏时暂停。

## 3. 行为引擎

### 动作模型

```json
{
  "schemaVersion": 1,
  "clips": {
    "groom_loop": {
      "fps": 8,
      "frames": [{ "image": "groom_0.png", "anchor": [32, 60], "dx": 0, "dy": 0 }]
    }
  },
  "actions": {
    "groom": {
      "weight": { "base": 1, "needs": { "boredom": 0.3 }, "cooldownSec": 120 },
      "when": { "onFloor": true, "hours": [7, 22] },
      "phases": [
        { "id": "down", "clip": "lie_down" },
        { "id": "loop", "clip": "groom_loop", "repeat": { "min": 2, "max": 6 } },
        { "id": "up", "clip": "stand_up" }
      ],
      "interrupts": {
        "drag": { "exit": "immediate", "to": "dragged" },
        "click": { "from": ["loop"], "exit": "jumpToPhase", "phase": "up" },
        "hunger": { "exit": "finishLoop", "phase": "up" }
      },
      "next": [{ "to": "sit", "weight": 3 }, { "to": "walk", "weight": 1 }]
    }
  },
  "fallback": "idle"
}
```

### 关键设计

- **脚不打滑：** 每帧都有锚点和位移。这是 shimeji-ee 的姿势模型，也是看过的方案里唯一能真正固定脚步的。
- **打断：** 每个动作声明自己如何退出。看过的项目都没有这一层，这是我们主要的改进点。
- **优先级：** 系统（拖动、下落）> 即时反应 > 需求驱动 > 闲置。
- **活的感觉：** 权重随状态变化、持续时间不固定、不立即重复同一动作、起跳前有预备姿势、对同一刺激逐渐失去兴趣。
- **昼夜眼色：** 按本地时间切换，白天蓝眼，晚上黑眼。素材只生成一套，用调色板替换眼睛颜色，不必把每个动作画两遍；切换时刻可配置，默认值待定。
- **避开的做法：** 全局可变状态、每帧让线程休眠、在配置里写脚本表达式、没有回退动作的随机选择。

### 引擎范围

- **第一版：** 固定步长循环、带校验的 JSON 加载器、锚点与位移、阶段执行器、打断表、优先级、带条件和冷却的权重选择、点击/拖动/抚摸判定、拖动与抛出和落地、多屏地面。
- **之后：** 需求和作息（持久化）、光标兴趣（追逐、扑击）、喂食、在窗口上行走。

## 4. 素材流程

参考 hatch-pet 的流程（基准图锚定、按动作生成、质检），但它的后处理不适合像素画：缩放用 LANCZOS、按帧居中，也没有网格识别和调色板。它的生成步骤依赖 Codex 的 `$imagegen`，其他脚本只依赖 Pillow，可以改写后独立运行。

1. **人工：** 选 3～5 张照片，写特征表（花纹、左右侧、尾巴、眼睛）。
2. **自动 + 人工确认：** 生成站姿基准图，再由它生成趴姿和坐姿基准图。
3. **自动：** 每组动作单独请求，附照片和最接近的基准图，每次生成 4～6 帧，保留多个候选。
4. **自动：** 去背景、按固定格切分。整只猫用同一个缩放比例（以头宽为准），底边对齐。
5. **自动：** 恢复像素网格，用最近邻缩小，透明度只留全透明和不透明，统一映射到基准图锁定的调色板。
6. **自动：** 检查帧面积和连续性、调色板覆盖率，生成总览图和 GIF。
7. **人工：** 最终确认像不像、动作对不对，用 Aseprite 修图。没有项目能自动判断“还是不是这只猫”。
8. **自动：** 打包成第 3 节的格式。

**素材注意事项：**

- 趴姿比站姿长，用宽画布并按底边对齐，比如 96×64，不要用竖向格子。
- 左右镜像会把不对称的花纹换到另一侧。这只猫目前没看到明显的不对称花纹，暂定走路动画直接镜像，详见 `cat-profile.md`。
- 白猫需要深色外轮廓，生成时要用高饱和的纯色背景，不能用浅色。
- 没有项目自带“趴下 → 舔毛 → 起身”的完整素材，需要我们自己生成。

## 5. 验证顺序

### 实验 A：素材（风险最大，先做）

用一只猫生成 `walk`（6 帧循环）和 `lie_down` → `groom`（各 4～6 帧），每组最多尝试 5 次。

| 检查项 | 通过标准（初始值，未校准） |
|---|---|
| 辨认 | 3 人从 4 张相似的猫照片中选出本猫，至少 2 人选对 |
| 花纹 | 特征表上的花纹，在可见的帧里至少 90% 位置正确 |
| 调色板 | 不超过 32 色，全部动作共用，没有半透明 |
| 稳定性 | `walk` 底边漂移不超过 1px，所有动作头宽差异不超过 10% |
| 动作 | 不提示的情况下，能认出走路、趴下、舔毛 |
| 修图 | 每组动作手工修改不超过 15 分钟 |

**未通过时：** 改用 Q 版风格，或从确认过的关键帧手工制作舔毛动画。

### 实验 B：macOS 26 原型（用占位图）

- 读取窗口列表时不弹权限，窗口位置和顺序完整，调用开销可接受
- 首次点击就能拖动，且不抢焦点
- 透明区域的点击能穿透到下层应用
- 跨屏不被裁切，全屏应用和台前调度下表现正常
- 闲置 CPU 低于 1%，移动时低于 5%
- 只装了 Command Line Tools（Swift 5.9、SDK 14.0，没有 Xcode）时，能用 SwiftPM 构建并在 macOS 26.4 上正常运行
